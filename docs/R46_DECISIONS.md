# R-46 decisions log

Append-only. `D-n (agent, date): decision. Why.` Keep both sides on merge conflicts.

D-1 (coordinator, 2026-11-10): Real-time is short polling with versioned deltas; broadcasting events stay for hosts that can run Reverb. Why: the shared cPanel host cannot run a WebSocket server (live /up/realtime is "degraded").
D-2 (coordinator, 2026-11-10): Dispatch advances on demand (every poll and the per-minute scheduler call Dispatcher::tick). Why: no daemons on the host; offers must still expire within seconds.
D-3 (coordinator, 2026-11-10): Money is integer minor units with ISO currency, versioned pricing rule sets, server-authoritative quotes with expiry. Why: brief section 6 pricing integrity.
D-4 (coordinator, 2026-11-10): Route-based fares require a real road route from a configured routing provider; straight-line distance is never billed. Why: brief section 10.
D-5 (coordinator, 2026-11-10): Turn-by-turn navigation hands off to the device's maps app; SOS creates an incident, notifies contacts and ops, offers SA emergency numbers; no claim of emergency dispatch. Why: honesty rules, no provider contracts.
D-300 (pricing, 2026-11-10): Pricing consumes other domains through pricing-owned ports (PricingRoutePlanner, PricingZoneLookup, EligibleSupplyCounter, DemandSignal, TollEstimator). Geo bridges are bound only when the geo classes exist; supply/demand/tolls default to "unknown/none" via bindIf. No straight-line route implementation exists. Why: parallel build without editing geo's files; honest unconfigured states.
D-301 (pricing, 2026-11-10): Money is a value object of integer minor units + ISO currency; IntegerMath refuses overflow; per-km rates are per 1 000 m; percentages and multipliers are basis points; rounding modes half_up/half_even/up/down. Why: no float may touch a fare (D-3).
D-302 (pricing, 2026-11-10): The demand multiplier never applies to tolls (deviation from the architecture section 4 sketch, contract updated), is only applied when the rule set enables it, is capped (validation max 3.0x) and is always shown as its own line. No demand signal exists, so there is no surge anywhere until the owner decides. Why: tolls are a pass-through cost; research shows hidden surge is the main fairness complaint.
D-303 (pricing, 2026-11-10): Rule-set resolution: in force + same country/currency + fitting constraints; specificity pickup zone 8 + area 4 + category 2 + time window 1; ties by latest effective_from, highest version, highest id. Commission plans: fleet 8 + area 4 + category 2. Why: deterministic, explainable, testable.
D-304 (pricing, 2026-11-10): Rule sets and commission plans are versioned by lineage; published/retired rows are frozen at the model (only retirement allowed, no delete); publishing n + 1 retires the live version at the new effective time. Why: every quote and fare must re-price exactly from (id, version).
D-305 (pricing, 2026-11-10): Bookable quotes are stored only for signed-in passengers, signed with HMAC-SHA256 (key derived from APP_KEY), valid 5 min, bound to passenger, route (75 m match tolerance) and category; anonymous estimates are never stored and get no promotions; unused quotes are deleted 24 h after expiry. Why: server-authoritative pricing, tamper evidence, POPIA minimisation.
D-306 (pricing, 2026-11-10): Without the geo zone seam the market is the configured default (ZA, ZAR, Africa/Johannesburg); with it, a pickup outside every service area or a pickup/drop-off in a restricted zone cannot be quoted. Why: works before geo merges, strict after.
D-307 (pricing, 2026-11-10): Finalisation: quoted fare stands within 15 % distance / 25 % duration; recalculated with the same version on passenger change (uncapped), overrun (increase capped at 20 % of the quote) or a shorter trip (passenger pays less); waiting and actual tolls always apply; an untrustworthy distance never moves the fare. Adjustments always sum to final - quoted. Values are per rule set. Why: upfront-fare fairness (research), never silently higher.
D-308 (pricing, 2026-11-10): Commission is charged on the trip fare only (base, distance, time, waiting, minimum, demand, cap, rounding, support adjustments); tolls are reimbursed to the driver at cost; booking/zone fees and tax are not commissioned; promotions are platform-funded. Without a plan, commission and net are null, never zero. Why: drivers must be able to verify the take per trip (research).
D-309 (pricing, 2026-11-10): Cancellation fees: passenger cancellations only; free before assignment, within cancel_free_minutes of assignment, and when dispatch reports the driver running late; no-show fee after the free waiting time at pickup; otherwise the cancellation fee; the promotion is returned. Why: common practice (research), fair to both sides.
D-310 (pricing, 2026-11-10): Promotions are evaluated at quote time and redeemed only in the ride-creation transaction with a row lock plus one conditional counter UPDATE; a refused redemption refuses the booking (re-quote). Remaining budget caps the discount. Why: limits must hold under concurrency on SQLite, MySQL and PostgreSQL.
D-311 (pricing, 2026-11-10): Ride categories are reference data installed by migration (idempotent, never overwrite edits). Business is inactive until business accounts exist; parcel is inactive and cannot be activated; accessible requires a vehicle feature that is not recorded yet, so no vehicle qualifies by assumption (fails closed). Why: honest catalogue.
D-312 (pricing, 2026-11-10): Migrations install no prices. The example ZA tariff (one rule set per category + 20 % commission, is_example, "Example tariff: review before launch", VAT none, no airport fee, whole-rand rounding) is installed by `ehail:pricing:install-example-tariff` (refuses in production without --force) and by DatabaseSeeder outside production. Why: the owner sets real prices; placeholders must never pass as real.
D-313 (pricing, 2026-11-10): FareCalculator::estimate/distanceKm (straight line, floats) removed; format helpers kept on the integer formatter; the legacy request form prices via LegacyRideFareAdapter and binds a ride_fares snapshot; existing rides keep their recorded decimals (shown as legacy). Tests updated: FareCalculatorTest, RideFareTest, RideRequestTest (behaviour legitimately changed), RidePaymentStateTest (rollback step count). Why: D-4, history untouched.
D-314 (pricing, 2026-11-10): The app renders JSON errors only for api/*; the pricing provider registers renderable callbacks so validation/auth/404 errors on pricing JSON paths (pricing/*, ops/pricing/*, fare-estimate*) are JSON. Other domains with JSON endpoints in the web group need the same. Why: a redirect is not an API error.
D-315 (pricing, 2026-11-10): audit_logs.subject_id is an integer, so quote audits use the rule set as subject with the quote ULID in meta; tamper detection is logged (an audit row would roll back with the refused booking). Why: schema constraint.
D-316 (pricing, 2026-11-10): FareFinaliser and FareAdjuster mirror the final total into rides.final_fare (decimal) because payments and history read it. Why: architecture section 0, existing columns mirrored.
D-317 (pricing, 2026-11-10): A category rating floor is not applied to a driver with no ratings yet. Why: new drivers would otherwise never qualify; dispatch may tighten.
D-318 (pricing, 2026-11-10): No new dependencies. Public estimate limiter 20/min per IP, quote limiter 30/min per user (config). Why: preference for none; abuse control.
